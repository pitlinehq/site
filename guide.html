Supported agents

For interactive Chat and supported approval controls, start a session from Pitline. Sessions started elsewhere can have fewer controls. Pitline shows only the actions available for the current session.

AgentStarted by PitlineStarted elsewhere
Claude CodeChat, messages, interruption and supported approvals.Conversation history and lifecycle monitoring. Terminal interaction; optional hook-based tool approvals.
CodexChat, messages, steering, interruption and approvals.A standalone TUI is history-only in Chat. A TUI connected to Pitline’s shared app-server can share control.
GrokChat, messages, steering, interruption and approvals while Pitline owns the session.Active-session discovery and read-only conversation history. Interact through its terminal.
OpenCodeChat, messages, interruption and permission responses.Read-only history for sessions exposed by the connected server; external sessions appear while active there.
PiTerminal access with hook-based lifecycle monitoring. No structured Chat or standalone agent-list card.
Other CLIsPlain terminal access. No structured Chat or agent-native approval controls; inferred activity is approximate.

Agent software and provider credentials are installed separately. Supported actions depend on the installed agent’s protocol and session ownership.

Start with one small task

After installing Pitline, open the local app. Choose New agent, your agent, and a Launch folder. Select Chat, then Start for that agent.

Ask the agent to explain the project. Follow its messages and tool activity, then give it a bounded change. Review any approval card before responding. Use interruption or steering when those controls are available. Switch to Terminal for a session’s terminal interface.

Monitoring sessions you already run

Supported agents can expose existing sessions to Pitline. If the app offers hook setup for your installed agent, follow that setup. For Pi lifecycle monitoring, install its extension and start a fresh Pi session:

Install Pi lifecycle integration
pitline integration install pi

Optional approvals for external Claude sessions

Install Claude hooks, then set remote_approval = "on" at the top level of your Pitline configuration and restart the daemon with pitline install-service. Start a fresh Claude session after installing the hooks.

Install Claude hooks
pitline integration install claude

This opt-in lets supported tool requests wait for a browser decision. If no decision arrives within ten minutes, control returns to Claude’s own permission flow. Some prompts, including plan approval in affected Claude versions, still need a response in Claude’s terminal. External Codex and Grok hooks are observational and do not grant browser approval control.

Terminals alongside your agents

Pitline is also a terminal multiplexer: organize native terminal sessions into workspaces, tabs and panes, and access them in your browser. Ordinary shells work without an AI agent. For example, create a native Bash pane from your local terminal:

Create a plain terminal
pitline new -t "Terminal" -- bash

Pitline can discover local Herdr sessions and expose their terminals, with available actions determined by the provider. Keep Herdr running on the same computer. tmux support is coming soon.

What survives reconnecting?

Closing a browser tab does not stop the session. Reopen Pitline to reconnect while your computer and the session remain running. Native terminal sessions can survive a Pitline daemon restart when the separate keeper service is healthy; they do not survive a computer reboot or keeper shutdown. Agent-process recovery depends on the integration.

Retained Chat history can be replayed; it is subject to local retention settings. Herdr owns its terminal history. The active terminal viewer controls its size, so opening a pane on your phone can resize the terminal.

Find your configuration

The first run creates a configuration file. Edit the existing file and preserve its other settings:

  • Linux: ~/.config/pitline/config.toml, or $XDG_CONFIG_HOME/pitline/config.toml when set.
  • macOS: ~/Library/Application Support/pitline/config.toml.

A custom PITLINE_CONFIG overrides this path. Settings such as bind, local_auth and remote_approval belong at the top of the file, before any table headings. Run pitline install-service after editing to restart an installed daemon.

Use Pitline from your phone

Your phone connects directly to the computer running Pitline. A private Tailscale or WireGuard network can connect them without opening a public port. Keep the computer awake and restrict access to your own devices with the network’s access controls.

  1. Set up the private network on both devices. Find the computer’s private network IP address.
  2. In your configuration file, set local_auth = "token". Set bind to the computer’s private network IP and port 7337, as shown below. Replace the example IP with your computer’s address.
  3. Restart Pitline, then print its local access token with the commands below.
  4. On your phone, open http://YOUR-COMPUTER-PRIVATE-IP:7337. Paste the token into the sign-in form and choose Sign in. Keep the token private: it grants control of Pitline.
Example configuration — replace the IP
bind = "100.101.102.103:7337"
local_auth = "token"
Restart and get your sign-in token
pitline install-service
pitline token

Pitline serves plain HTTP. The private network supplies transport encryption between its devices; token authentication controls access to the app. Choosing a port such as 8443 does not enable HTTPS. For access outside an encrypted private network, use a properly configured HTTPS reverse proxy and keep token authentication enabled.

A bind address of 0.0.0.0 listens on every IPv4 interface, including LAN interfaces. With authentication off, every reachable client can control sessions. Bind to the intended private address and enable authentication before connecting from another device.

After binding only to the private address, use that address on the computer too; the loopback URL will no longer be listening. Hosted relay access, native mobile apps and push notifications remain planned. Phone access today is through the browser.

Troubleshooting

The app will not open

Run pitline doctor and check its daemon, keeper and environment results. Confirm the service installation succeeded. Run pitline bind to inspect the configured address. For phone access, check that both devices are connected to the private network and its access controls allow the connection.

My agent or project is missing

Install and authenticate the agent on the same computer, then rerun pitline install-service so the service picks up its executable path. The launch-folder catalog initially searches Git repositories within two levels of ~/code, if that directory exists, or your home directory otherwise.

Add a launch root to your configuration for another project location, using a unique id. This example also lists ordinary folders:

Example launch root
[[launch_roots]]
id = "projects"
label = "Projects"
path = "~/projects"
kind = "repo-root"
max_depth = 2
include_plain = true

Replace the path with your project directory, restart using pitline install-service, and reopen the launch form. Paths outside configured roots are not available to browser launches.

An approval or message control is unavailable

Check the agent table and whether Pitline started the session. A readable transcript does not imply writable Chat. Use the session’s terminal for prompts that its integration cannot resolve.

I need more help

Contact support with your OS, Pitline and agent versions, the steps that failed, and relevant pitline doctor output. Remove access tokens, credentials and private project content before sharing.

Update or remove Pitline

Update

Read the release notes, then rerun the shell installer or replace your manual installation with the new archive. Run the commands below to refresh the service and check it:

Refresh and check the service
pitline install-service
pitline doctor

The service installer restarts the daemon and leaves an already running keeper in place. Finish critical agent work before updating; structured agent recovery varies by integration.

Remove

Finish active work first. The following command stops and removes both the daemon and keeper services, ending sessions that rely on them:

Stop and remove services
pitline uninstall-service

Then remove the pitline executable from the location used by your installer or manual installation. Service removal keeps your configuration and local history. If you installed agent hooks or the Pi extension, remove the Pitline entries from that agent’s configuration before deleting the executable.
